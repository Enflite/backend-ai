# Deployment and operations

Use `backend/.env.example` and `frontend/.env.example` as inventories, not deployable secrets. Supply secrets through the deployment secret manager. Run migrations before rolling out the API. The production database principal must be a non-owner without `BYPASSRLS`; otherwise PostgreSQL owners bypass RLS and only the application query filters remain.

Required production dependencies are PostgreSQL 16 with `pgcrypto` and `vector` (>= 0.7.0 for the HNSW vector index; the RAG retrieval path runs filtered vector scans with tenant predicates, which depend on pgvector 0.7.0's iterative scan fix to return correct results under filters), S3-compatible private object storage, an HTTP malware scanner, approved OpenAI-compatible chat and embedding services, TLS termination, and an enterprise identity integration. SyteLine is optional. Document extraction (PDF, DOCX, XLSX, HTML, CSV, Markdown, text) runs locally inside the API process with bounded archive expansion; no separate extractor service is required.

The backend container is multi-stage, deterministic (`npm ci`), non-root, and exposes `/health` and database-aware `/ready`. `COOKIE_SECURE=true`, `MALWARE_SCAN_MODE=http`, `MALWARE_SCANNER_ENDPOINT`, explicit `CORS_ORIGIN`, short access-token lifetime (`JWT_EXPIRES_IN`, default `15m`), and high-entropy `JWT_SECRET` (>= 32 chars; documented placeholders are refused at startup in production and warn loudly elsewhere) are mandatory in production. Do not expose model, embedding, storage, scanner, database, or SyteLine endpoints directly to browsers.

The server shuts down gracefully on SIGTERM/SIGINT: it stops accepting connections, ends active SSE streams via a `preClose` hook (hijacked responses are invisible to `server.close()`), lets in-flight requests finish, then drains the PostgreSQL pool. The drain is bounded by `SHUTDOWN_DRAIN_MS` (default 15000); when it expires, remaining connections are force-closed so a stuck client cannot delay shutdown past the platform's SIGKILL. Crashed ingestion jobs are reclaimed on the next startup (`recoverIngestionJobs`), including documents stuck in PENDING/PROCESSING without an active job row (drained in batches of 20, capped at 500 batches per startup); jobs that exhaust retries become `FAILED/POISON_MESSAGE` (poison handling runs before orphan recovery, and the associated document is also marked `FAILED` so it cannot be re-enqueued into an infinite poison loop). Embedding requests retry transient 5xx/429 with backoff but never retry after cancellation, and abort-aware backoff keeps cancelled jobs from lingering.

`npm run build` compiles TypeScript and copies `src/db/migrations` into `dist/src/db/migrations`. The migration runner resolves its migrations directory relative to the running module (`path.join(__dirname, 'migrations')` in `src/db/migrate.ts`), so both entry points work: `npm run migrate:prod` (`node dist/src/db/migrate.js`, the production image path — the compiled migration module reads the copied SQL files) and `npm run migrate` (`tsx` from a source checkout, for dev or one-off job containers). Never `tsx` outside development. Migrations apply in filename order and are append-only; 004 renames the legacy `COMPLETED` document status to `READY`, 007 adds per-model tuning (`request_timeout_ms`, `max_tokens`, `temperature`, `fallback_model_id`), 008 fixes query-plan indexes and drops redundant ones, 009 adds refresh-reuse detection columns, 010 adds login-lockout columns, 011 removes the dead `tool:admin`/`user:manage` permissions, 012 keeps a rolling history of superseded refresh-token hashes, 013 applies `FORCE ROW LEVEL SECURITY` so table owners cannot bypass the tenant-isolation policies, and 014 drops the remaining redundant indexes (`idx_audit_events_user`, `idx_documents_tenant_classification`, `idx_users_email`).

Index builds on populated tables: plain `CREATE INDEX` blocks writes while it runs, and `CREATE INDEX CONCURRENTLY` cannot execute inside a transaction. A migration file that starts with the header line `-- migrate: non-transactional` runs outside a transaction, one idempotent statement per file (the runner rejects multi-statement files; prefer `CREATE INDEX CONCURRENTLY IF NOT EXISTS`). Validate the upgrade on staging first — a failed non-transactional migration can leave its statement applied, and `schema_migrations` is recorded only on success.

Create operator accounts with `npm run create-user -- --email <email>`: the password comes from a no-echo TTY prompt or the `BACKEND_CREATE_USER_PASSWORD` environment variable (for automation; export it, never inline it on a command line). `--password` is not accepted as a CLI argument — it would be visible in shell history and process listings. Minimum length is 12 characters and `UNKNOWN` clearance is rejected.

Audit NULL-tenant writes are safe under 013's `FORCE ROW LEVEL SECURITY` and need no extra policy: migration 003 gives `audit_events` a dedicated `tenant_isolation` policy whose `WITH CHECK` explicitly allows `tenant_id IS NULL` when no tenant context is set, and `recordAudit` takes the non-tenant query path (plain `query`, no `app.tenant_id`) when the caller has no tenant — e.g. pre-auth login failures — so the insert passes the policy even for a table-owning role. Tenant reads stay isolated (`WHERE tenant_id = $1` plus the policy), and NULL-tenant rows are invisible to tenant-scoped reads. Audit persistence behavior is governed by `AUDIT_FAIL_CLOSED` (default true in production, false otherwise): when true, a failed audit write aborts the request instead of logging and continuing, so a database outage cannot silently erase the record of what happened during it.

Optional tuning: `RAG_SIMILARITY_THRESHOLD` (0–1, default 0 = disabled) drops low-relevance chunks after the hybrid rerank so weak matches never reach model context. AI safety limits: `AI_MAX_RESPONSE_CHARS` (default 65536), `AI_MAX_TOOL_ITERATIONS` (default 5), and `AI_TOOL_OUTPUT_MAX_CHARS` (default 8000). Per-model tuning lives in the `models` table (`request_timeout_ms`, `max_tokens`, `temperature`, `fallback_model_id`) and is managed by AI Admins through the model registry, not environment variables.

Validation without the actual internal providers can cover builds, migrations, policies, request boundaries, and adapters, but it cannot establish real inference quality, embeddings, scanning, extraction, storage, or SyteLine connectivity.
